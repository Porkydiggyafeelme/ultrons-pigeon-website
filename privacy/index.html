Privacy policy

A review draft describing the development-stage application and its website. This is not a final policy, legal advice, or suitable for submission to a mail-provider API program.

OWNER REVIEW REQUIRED — DO NOT RELY ON OR SUBMIT THIS DRAFT. Operational facts remain unverified. Confirm the data inventory, account-removal behavior, retention and diagnostics before final publication.

Last reviewed: 25 October 2026 · Status: development draft · Operator: Marcus Waters, independent developer, operating personally (not through a registered company) · Operating jurisdiction: Arkansas, United States · Privacy and support: marcus.waters@me.com.

1. Scope and current status

Development Codename (the “Application”) is a temporary codename for a desktop email client with a Windows version under active development and a macOS version also in early development. Its final name has not been selected. Both versions are in private development; the macOS application has not been built, run or released on a Mac. The owner confirms that no external beta testers have connected real mail accounts and no real mail was accessed during development. This draft describes current evidence and intended functions; it does not claim all plans are operational.

The project website is a static information site with no account registration, contact form, newsletter, analytics script or advertising feature. GitHub Pages is operated by GitHub. Site requests may be processed under GitHub’s Privacy Statement and applicable platform terms; this project does not control GitHub infrastructure logs.

2. Mail and account data

Platform status and privacy safeguards: The current desktop implementation is Windows-specific. Development work toward macOS includes evaluation and adaptation of shared code, but a Mac-native interface, macOS secure credential storage, platform-specific data controls, and actual macOS integration and security testing have not been completed. The Windows DPAPI protection described below applies to Windows only; it does not represent an implemented Mac Keychain protection system. No Mac version is currently available to users, and macOS-specific data handling must be verified and disclosed before any Mac release.

The intended mail functions require access to data from a provider after a user chooses to connect an account and grants access. Depending on provider and enabled features, this may include account identifiers and addresses, authorization tokens or provider-specific credentials, folders and message identifiers, sender/recipient details, subjects, message bodies, attachments, read state and synchronization cursors. Provider data is needed to display and synchronize mail and carry out user-requested operations such as sending.

Current code has a Microsoft browser sign-in and mail synchronization path, but use requires the owner’s Microsoft app registration and live validation. Gmail backend work exists, but full API authorization and live testing are incomplete. Yahoo/AOL are not operational. Other providers are being evaluated; users may enter server settings for supported manual connections. Provider availability, permissions and data handling must be documented before release.

Sign-in, sending and synchronization necessarily communicate with the selected provider. The provider separately processes data under its own terms. The app is intended to cache mail locally for offline use. Its source includes an encrypted SQLite mailbox store with a database key protected using Windows DPAPI for the current Windows user. This is implementation evidence, not an independent security assessment or a guarantee against device, account, operating-system or provider compromise. The exact data stored by each feature and protection for temporary files, backups and exports still require release validation.

3. Synchronization, storage and retention

The intended sync retrieves provider mail to a local cache and applies changes during later sync. A local encrypted storage path exists in source. No project-operated hosted mailbox database or public mail-processing service is confirmed. This does not mean data never leaves the device: sign-in, sending and synchronization exchange information with the chosen provider. Future features could add processing that would require advance disclosure and consent.

Account-removal policy decision (implementation not yet verified): When a user removes an email account, the Application must stop synchronizing that account, remove its locally stored credentials, and delete that account's local cached messages, attachments and search indexes. Removing an account must not delete messages from the email provider's servers. Local-only unsent drafts must be preserved in a separate, locally stored Local Drafts section when their email account is removed. The user must be able to reopen and edit these drafts, export them, reassign them to a different connected email account, or explicitly delete them later. Reassignment must not send a message: drafts may be sent only through a separate, deliberate user-initiated Send action. Account removal, synchronization, reassigning a draft, beta expiry and other background processes must never automatically send or silently delete these preserved drafts. This is the developer-approved intended behavior, not a claim that all removal, draft-storage and cleanup paths have been implemented or tested in the current application.

Provider authorization revocation (approved policy; implementation not yet verified). Removing an account must immediately stop synchronization and other account-specific background access, clear locally held sign-in tokens, passwords or app passwords, and attempt to revoke the Application's authorization with the email provider wherever that provider supports revocation through an available and authorized mechanism. Local cleanup must proceed even if the remote request is unsupported, fails or has an uncertain outcome. The Application must clearly distinguish a confirmed provider-side revocation from local sign-out, an attempted or failed revocation, and an unsupported revocation. If remote access cannot be confirmed revoked, it must tell the user and give provider-specific instructions for reviewing and removing the Application's access in the provider's security or connected-app settings; for app-password connections this may require the user to revoke that app password through the provider. Removing an account must never delete messages or other data from the provider's servers. Any preserved Local Drafts must remain available and must never be sent automatically. Provider capabilities and the actual status reporting must be tested before this policy is finalized.

Connected-account cache retention (approved policy; enforcement requires verification). For Gmail, Outlook, Hotmail, and other non-Yahoo mail accounts, the Application is intended to retain locally cached messages and attachments while the account remains connected, supporting offline access. Synchronization must reflect provider-side message changes and confirmed deletions, and removing an account must clear that account's cached mail as described above. Any shorter retention or deletion rule required by a provider takes precedence. This decision does not override local-only draft preservation or provider-specific limits.

Local technical diagnostic logs (approved design; not yet verified). Ordinary technical logs, if stored by the Application, must stay on the user's device and be automatically deleted within seven days of creation. They must be sanitized to exclude mailbox content, credentials, account identifiers and identifying file paths. Such logs must not be uploaded automatically. Their retention and cleanup must be implemented and tested before this policy is finalized. This is separate from the default-off, explicit-opt-in encrypted crash-report queue and from the 30-day limit on reports received by the developer.

Message and draft exports (approved design; not yet implemented or verified). User-created exports of email messages and locally preserved drafts must be encrypted by default. Users may deliberately choose a supported unencrypted format, such as TXT, EML or JSON where available, only after a clear warning before saving that the file could reveal private message or draft information to anyone with access to it. The Application must never silently fall back to plaintext if encryption fails. Once the user saves an exported file, they control where it is stored, shared and deleted; the Application must not silently delete or alter that file during account removal, draft cleanup, build expiry or other background operations. A user-created export must not be uploaded or sent by the Application without a separate explicit action. Application-managed staging or temporary export copies remain subject to their own verified cleanup requirements. Portable password protection (approved design; not yet implemented). The default encrypted export must use a password-protected, documented format that can be opened on Windows and macOS with compatible software, without relying solely on Windows DPAPI, a Mac-only key store or the original device. Users must choose an export password and supply it again when opening the file. The Application must not save, retain, synchronize, transmit, log, upload or include export passwords in reports; passwords may be handled transiently in memory only as needed to encrypt or open an export and must never be embedded in the exported file. Before creating the export, warn users that losing or forgetting its password could make the exported messages and drafts permanently unrecoverable, with no developer password-recovery service. The exact export format, encryption implementation, cross-platform compatibility and recovery limitations still require implementation and independent testing. The current prototype includes explicit plaintext sample-message TXT and local draft JSON exports; encrypted-by-default portable password-protected exports have not yet been implemented or independently tested. This approved design does not claim existing prototype exports are encrypted.

Other retention and cleanup remain under review. Preserved Local Drafts are intended to remain available until the user explicitly deletes them; their storage and recovery behavior must be tested. Retention periods and cleanup rules for database journals, application-managed temporary copies (including export staging), and backups are not yet fully established or validated. User-created exported files remain under the user’s control as described above. Windows token-cache cleanup and confirmed provider-side authorization revocation, fallback guidance and consent-removal handling still require implementation verification. Provider copies and backups are governed by that provider. These behaviors must be confirmed before this becomes a final policy.

Yahoo-specific 12-hour cache policy. Yahoo Mail is excluded from the connected-account retention policy above. The developer has directed that locally cached Yahoo mail data expire no later than 12 hours after each item's retrieval, including local message content, attachments and indexes, without deleting mail from Yahoo's servers. The developer reports that this requirement has been added to the Application, but its complete enforcement and cleanup across temporary files, backups and restart paths has not been independently verified. Yahoo's published developer API terms and guidelines generally restrict retaining Yahoo user data beyond 24 hours unless an exception or applicable agreement provides otherwise; a 12-hour local cache alone does not establish compliance or grant access. The Application does not currently have approved or operational Yahoo/AOL Mail OAuth access. The applicability of Yahoo's retention rules to native desktop IMAP/SMTP access and any provider-specific conditions still requires confirmation from Yahoo. See Yahoo Developer Access and Yahoo API Terms.

4. Optional AI-assisted advanced spam detection and removal

Limited purpose of AI integration. The Application's planned AI integration is exclusively for advanced spam detection and spam-removal assistance, including evaluating suspected junk, phishing, impersonation and fraudulent messages as possible spam. AI is not intended to compose or send mail, manage accounts, change synchronization or other ordinary email functions, or make unrelated mailbox decisions. AI provides an advisory assessment of suspected spam; it has no authority to delete, move or otherwise modify messages, and its output alone cannot authorize removal. Any future automatic spam removal must be separately enabled by the user and carried out by application-controlled, deterministic rules with validated high-confidence criteria, safe-sender protections and review of uncertain cases. AI failure or absence must not interfere with ordinary email operations.

Current development status. The application currently provides only an unassessed security-review simulation. A working AI model integration, advanced spam analysis, automatic spam filtering and permanent spam removal have not been activated or independently validated. No mailbox content is currently transmitted to an external AI service. Future external AI analysis, where permitted by the applicable mail provider, requires an explicit user choice and disclosure of the selected content, destination and purpose; enabling spam detection does not automatically authorize a cloud upload.

No Yahoo API data is currently sent to, or proposed for transfer to, a third-party AI or cloud provider. Yahoo API data must not be assumed shareable with a third party. Any future proposal involving Yahoo data must first be checked against Yahoo’s then-current developer requirements; if third-party transfer is prohibited, that processing must not be implemented. For any provider whose rules permit external analysis, the exact content, recipient and purpose would need to be disclosed and user-enabled before use.

Yahoo’s developer requirements call for accurate disclosures about collection and use of Yahoo API data, user controls, security standards and consent for each use case. Yahoo is not operational in the Application at present. Any future Yahoo access request, requested permissions and described use cases must match the Application’s actual current and specifically planned functionality; a request must not claim capabilities that do not exist or are not planned. The proposed use case and final privacy disclosures must be reconciled with the actual product behavior before any Yahoo API submission.

5. Diagnostics and reporting

Local logs are not crash-report uploads. Ordinary technical logs stay on the device, are not uploaded automatically and expire within seven days. They are separate from the encrypted crash-report queue, which requires explicit opt-in and has its own local pending-report expiry; developer-received reports retain their previously approved 30-day limit.

No general application analytics, crash-reporting or diagnostic-reporting service is confirmed as deployed. Source includes an optional path for submitting limited, allowlisted public mail-server settings (domain, server hosts, ports and encryption modes), only when an owner-configured HTTPS endpoint and enrollment credential exist. The owner confirms no such endpoint has been deployed or used. The report payload excludes message content and mailbox credentials.

Planned optional crash and diagnostic reports (not yet operational). The Application is intended to offer automatic transmission of sanitized diagnostic and crash reports only after the user explicitly opts in; the setting must be off by default and users must be able to disable it. The only approved report fields are the Application version, Windows version, error code, error timestamp and sanitized crash stack traces. Stack traces must exclude identifying local file paths, usernames, email addresses, account or device identifiers, message content and other personal or secret data. Reports must never contain mailbox data (including message headers, subjects, bodies and attachments), passwords, app passwords, authentication tokens or other credentials. Reports must be assembled from a strict allowlist, sanitized before transmission, and independently tested with representative and adversarial crash data to confirm that forbidden information is not exposed. If sanitization fails or cannot be verified, automatic transmission must not occur. Adding any further report fields requires updated disclosures and review before activation. The approved retention policy requires that diagnostic and crash reports received by the developer be kept for no longer than 30 days after receipt and then automatically deleted from developer-controlled systems, including any developer-controlled backup copies where technically feasible. If applicable law requires preserving a specific report for longer, only that report may be retained for the legally required period and must be deleted once that obligation ends. No broader retention exception is authorized. The selected destination is an owner-controlled HTTPS receiver implemented using a Cloudflare Worker, which will validate and route approved crash reports into categorized issues in the developer's private GitHub repository (not the public project website). This is not an email-reporting system: reports are never sent from a user's mailbox, and no email sender address or provider-mail authorization is used. The same Worker also has a separate route for user-provided public IMAP/SMTP server-settings candidates, which are never mixed with crash data. GitHub crash issues use the report:crash label and a logical title resembling crashreport-xxxx.txt; provider-settings issues use report:provider-settings and providersettings.txt. These names do not represent files committed into permanent Git history. No Worker endpoint, D1 database, crash reporting receiver or GitHub issue publication is deployed or enabled at present. Before activation, the Worker must enforce TLS, strict server-side field validation, bounded requests, abuse limits, restricted administration and tested deletion procedures. Cloudflare and GitHub will process submitted reports and may process incidental transport metadata, such as connection IP addresses and platform logs; their infrastructure and retention policies are relevant to this design. The precise public HTTPS receiver address, credentials, any service-specific logs and deletion verification remain outstanding. GitHub's issue-deletion capability must be tested so developer-received reports are removed within 30 days, but infrastructure backups, notifications and other copies outside the developer's control cannot be promised erased. Accurate processor disclosures, user opt-in, end-to-end tests and approval remain required before any automatic report is transmitted. These details and the user's informed opt-in are required before any reporting is activated. This is a design requirement, not a claim that automatic deletion or a reporting service is operational. Choosing this design does not mean automatic reporting currently runs or that production sanitization has been tested.

6. Sharing and security

The application is not intended to sell mailbox data or use it for advertising. Mail data is exchanged with the provider selected by the user for requested mail functions. No other third-party recipient of mailbox content is currently confirmed. This is not permission for future external processing; recipients and purposes must be reviewed and disclosed before use. In particular, this draft does not authorize or imply third-party transfer of Yahoo API data.

Development includes a local encrypted mailbox store and a key protected for the current Windows user. Microsoft sign-in uses a provider-hosted browser flow; supported manual credentials are intended to be protected separately from the ordinary mail database. These controls are not independently certified, and live-account validation is incomplete. Do not send passwords, tokens, private keys or mail content to the project through this website.

7. Choices, requests and changes

Account connection is intended to be user initiated. The approved account-removal behavior is described in Section 3; the actual controls, their cleanup results, and any export features and privacy-request handling remain to be verified. Provider-side app authorization revocation must be attempted where supported; where unavailable, unsuccessful or uncertain, the user must be told clearly and provided with provider-specific instructions to revoke access manually. Removing a local account must never be represented as confirmed provider-side revocation without verification. For privacy questions, requests about account data, and general application support, contact marcus.waters@me.com. The remaining data-control procedures must be verified before this policy is finalized. Users may also use their provider’s privacy and account controls.

The Application is intended for users aged 13 and older and is not directed toward children under 13. People under 13 should not use the Application or send personal information to the published privacy and support contact. If you believe a child under 13 has provided information directly to the developer, contact marcus.waters@me.com so the concern can be reviewed and handled as required by applicable law. Age verification or enforcement within the Application has not yet been independently verified. A dated final policy and verified data-control procedures are still needed before general release.
